# 项目 AGENTS.md

## 项目名称

造价智算-工程造价辅助智能体

## 项目纲领（竞赛第一原则）

- 本项目首先是一项竞赛作品。赛事核心评审要求必须原文记住并贯穿后续工作：**“本次比赛重点考察项目的创新性和作品完整性。”**
- 已确认赛事通知原文：**“本次预赛统一采用现场展示+答辩的方式：8分钟作品介绍（含展示）、2分钟答辩，请各位选手提前做好作品准备和材料编制。”** 本通知中的“预赛”与项目现有文档所称“复赛”指同一场比赛，后续统一按同一赛制执行。
- **赛制硬门禁：8 分钟作品介绍包含现场展示。** 制作或修改 PPT、逐页演讲稿、产品演示脚本、计时表和答辩材料时，必须把 PPT 讲述、现场展示、页面切换和结尾收束共同纳入这 8 分钟；2 分钟答辩单独准备、单独计时。不得把现场展示另算时间，不得用答辩时间补足作品介绍，也不得只按纯讲稿时长计算 8 分钟。
- “创新性”不是堆叠大模型、机器人或页面数量，而是证明本项目把专业 Skill、结构化规则、大模型解释、人工复核、场景协同和可信知识记忆组合成了具有专业价值的新型造价智能体。
- “作品完整性”不是功能清单看起来很多，而是至少有一条真实、可运行、可验证、可演示、可追溯、异常可降级的端到端业务闭环；当前主闭环为“任务进入 → 选择专业 Skill → Excel 编制 → 规则匹配 → 风险复核 → 多人协同 → 成果输出 → 经验沉淀 → 后续复用”。
- **竖屏适配零影响宽屏硬门禁：任何 iPad 竖屏、手机、触控或其他窄屏适配，都必须以“不影响现有宽屏界面一分一毫”为绝对前提。** `>=1025px` 的页面结构、坐标、尺寸、比例、字号、间距、颜色、边框、圆角、阴影、可见文案、控件、交互、折叠状态、业务状态和性能表现必须保持原样；适配规则应采用仅在窄屏断点生效的独立隔离层，并在交付前使用实施前后的宽屏基线逐项对照验证。凡无法证明宽屏零变化的竖屏方案不得实施，也不得以“响应式统一调整”为理由顺带修改、重构或美化现有宽屏页面。
- 后续做产品规划、开发排期、UI 设计、PRD、测试、发布、PPT 和现场演示时，都必须回答两个问题：本次工作是否增强了创新表达，是否补齐了作品闭环。两者都没有明显贡献的新增功能应降低优先级，但稳定性、真实性、交付安全和演示风险修复除外。
- 赛前发生范围冲突时，优先补齐一条能完整跑通的真实主线，不为展示效果制造假数据、假按钮、假进度或未实现能力；`[已完成]`、`[进行中]`、`[待开发]` 必须诚实区分。
- 面向参赛评委的统一产品口径以 `README.md`、`00-PRD/00-产品总览.md` 和 `00-PRD/02-当前版本计划.md` 为准；其中 `00-PRD/00-产品总览.md` 的“参赛创新与作品完整性主线”负责展开本纲领。

## 协作规则

- 当前项目是从 WeAgent 平台迁移到本地电脑运行的软件原型；软件对外名称已升级为“造价智算”，定位为“工程造价辅助智能体”，当前核心场景仍覆盖长输管道勘察测量最高投标限价编制。
- 原始资料、测试表和答案表不直接改动。
- 生成文件放在程序运行输出目录中，不覆盖原始输入。
- 仅本项目适用：从现在开始，新生成的文件名不要再追加 `codex`、`【codex】`、`-codex`、`codeX` 等尾缀；除非用户明确要求保留历史命名，后续输出、提示词、报告、临时结果、截图、素材和项目说明文件都使用不暴露 Codex 的命名。
- 复赛 PPT 按版本成套归档：每个版本必须在 `07-汇报PPT 和 演示素材/00-汇报PPT和素材【同步】/260715-【复赛PPT】/03-定稿/` 下建立独立的 `日期-【Ai稿和AiPPT】造价智算-复赛PPT内容稿与逐页演讲稿-vX.X.X【主要/历史】/` 目录；该版本主文稿放在目录根部，对应的完整逐页 PPT 图片集放在同一目录下。不同版本的文稿和图片不得混放，新增页过程图须与“完整图片集”明确区分，便于从文稿版本直接定位对应视觉稿。
- 历史知识库、经验池模板、输入样例和兼容脚本里已经存在的“管勘智算”文件名暂时保留，不做批量重命名；除非用户明确发起迁移任务，否则不要为了品牌升级改坏真实路径引用。
- 知识库使用二维 Excel 数据库，不把价格裁决交给大模型；固定知识库为 `03-知识库-二维数据库制作/【数据库】【导入】.xlsx`，其中 A-H 用于基价，J-M 用于调整系数第二层经验提示。
- 大模型后续只作为报告润色、待复核解释、自然语言助手，不直接输出最终单价。
- 用户说“git存档”时，或本项目更新版本号 / CHANGELOG / 当前版本计划并完成验证后，视为触发一次本地 Git 存档：先用 `git status --short` 和 `git diff --stat` 做轻量检查，再执行 `git add` 与 `git commit`；提交信息和交付说明必须写清本次存档备注。该操作只做本地提交，不等同于运行代码版 zip 存档，也不得自动 `git push`。
- 造价智算与 `D:\Codex-Temp\260712-【数字化造价助手】` 之间使用 `D:\Codex-Temp\260712-【数字化造价助手】\00-docs\02-架构与集成\03-造价智算宿主交接状态.md` 作为跨项目交接信箱。凡涉及数字化项目助手的菜单、iframe、启动、主题、联调或发布，开始前必须读取该文件；造价智算侧完成相关工作后，必须更新“宿主最新交接、当前状态、下一责任方和更新时间线”，不得只在聊天中口头交接。

## 项目经验 / 注意事项

- 从历史控制价重新提炼规则时，逐字段区分原始输入、历史调整和已批准的计价依据；输入输出有差异不能为对齐答案改量或改系数。综合取费乘数须先确认费用构成再拆分，历史候选规则经审核与正式业务回归后才可接入生产资产。

- Gork 任务哨兵的“正在运行”必须同时核对批量匹配 attempt 记录和仍被生产者持有的锁；`business_tasks.status=processing` 与更新时间只是登记信息。结果计数只关联相同 attempt 的已提交状态，完成记录与锁释放之间的读取竞态须复查终态。
- 批量匹配可能在 Gork 两次轮询之间结束；只读 `/api/task-monitor/current` 的 `recent` 保留最近 20 条有 attempt 的终态快照供补报，`task` 始终只代表实际运行任务。Gork 首次读取应建立基线，避免重放旧提醒。
- 转换、预警、报告、协同复核的短节点由真实业务入口写入独立持久事件；监控 GET 只读，不能从任务登记状态臆测节点。协同“已发起”与“已送达”分开，后者须同时核对成果和复核卡片 `sent` 回执。
- Gork 的 `report_generated` 只对应用户执行“输出风险报告”且风险正文成功写入最终 Word；转换、匹配和预警阶段虽会写入或更新过程 Word，也不能发布该播报节点。
- WeAgent 历史经验表明，主价格判断不宜依赖大模型自由生成或相似度最高候选，应优先采用字段硬校验和归一化后的结构化匹配。
- 常见归一化差异包括全角半角括号、比例前缀、空格、换行和价格列名称差异。
