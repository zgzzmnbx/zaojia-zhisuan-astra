# AI 增强匹配与离线双模式——实施方案

文档版本：v1.0.0｜2026-09-05｜目标 v5.24.0，当前未实现。

需求以同目录 `PRD.md` 为准；下面的新增模块、字段与端点是实施建议，Luna 可依据现有代码调整命名，并把最终契约写回本文件。语义、权限、离线能力和验收标准不得自行降低。

## 1. 已核对的接入事实

- `backend/app/main.py` 的 `/api/process` 生成 `matching_status=pending` 的待匹配预览；`/api/process/batch-match` 调用冻结 Skill 对应的 `FillEngine.fill_workbook()`，随后重算、生成报告并同步 Task。
- `backend/app/fill_engine.py` 当前按表头/列映射解析必要字段。`fill_assist.py` 组织并排序基价候选，现有模型主要解释候选，不能把本次规划写成已上线能力。
- `backend/app/llm.py` 当前通用调用为同步网络请求，单次超时 90 秒，最多 3 次网络尝试。新核心匹配不能直接继承此等待行为，也不能修改其默认参数而影响原问答。
- `SkillRuntimeContext`、原 `process_options`、任务目录和手工修改记录是复用点；不得复制出第二个项目台账、第二套专业规则或第二套协同状态机。
- `tools/verify_v31_task_acceptance.py` 是现有正式验收脚手架，但其顶层 `passed` 条件未覆盖所有已计算差异项。Luna 必须检查 sheet/行覆盖、全值、隐藏行等结果，不能只看脚本退出码就声称无损。

## 2. 模块分层与所有权

建议新建 `backend/app/ai_matching/`，各文件仅负责本职责：

| 建议文件 | 职责 | 禁止跨界 |
| --- | --- | --- |
| `contracts.py` | 模式、来源、映射、候选、确认、事件的类型及严格校验 | 不裁决价格 |
| `workbook_reader.py` | 一次顺序读表、块识别、来源坐标与覆盖清单 | 不改共享合并/归一化规则、不执行宏 |
| `structure.py` | 表级理解请求、声明式映射与人工确认方案 | 不接受模型代码或价格 |
| `candidates.py` | 复用可信资产检索、候选快照与硬条件过滤 | 不把检索失败当作有答案，不修改原候选排序 |
| `semantic.py` | 有限候选辨析、缺失条件与拒绝推荐 | 仅输出允许 ID 和依据，不写 Excel |
| `client.py` | 独立异步/可取消请求、总预算、限流、脱敏错误 | 不改变原通用模型客户端的默认行为 |
| `orchestrator.py` | 模式分派、阶段运行、部分失败与机械降级 | 不复制原匹配算法 |
| `store.py` | 本 Run 的提案、审计、版本、幂等与恢复 | 不另建业务 Task 状态机 |

前端建议新增局部组件承载模式设置、理解确认、候选证据和降级状态，复用现有 Dialog、预览与 Task。`App.tsx` 和 `styles.css` 只做必要挂载与局部样式；开工前已有改动必须保护，禁止整体替换或格式化。

`fill_engine.py`、`adjustment_rules.py`、知识库/规则资产视为受保护核心。确需抽出最小只读适配函数时，先增加行为回归，证明机械结果未变。新增接口和阶段必须只服务本模块，不改变已有 API 对旧调用者的返回结构与语义。

## 3. 双路径执行与确认顺序

```text
上传 XLSX，冻结 Task / Skill / 输入哈希 / 请求模式
  ├─ mechanical → 原 process → 原预览 → 原 batch-match → 原成果
  └─ ai_enhanced
       → 程序读取、行覆盖与资源检查
       → 模型结构理解（已支持标准结构可直接使用机械解析，不强制调用）
       → 映射/要素预览；影响计价的 AI 推断先确认
       → 保留原有“批量匹配”按钮与操作
       → 原规则处理明确记录＋检索剩余疑难项
       → 疑难组模型辨析，展示建议/证据/缺失条件
       → 逐字段确认 → 可信来源取值 → 受控写回
       → 原重算/报告刷新 → 真实成果、审计、剩余待复核
```

- AI 辨析前的机械候选集来自原输入或已人工确认的映射/要素。尚未确认的语义字段只能在提案副本中试匹配，用于生成建议，不能混入正式引擎输入。
- 两轮模型依赖之间允许人工确认等待；“两轮”不含人工时间、失败重试，也不意味着每张表只发两次 HTTP 请求。证据中分别统计。
- 用户可拒绝提案、修正映射、继续机械流程。拒绝记录不得由后续批量操作偷偷采用。
- 新模式可以有规则处理完成而 AI 提案仍待确认的状态。沿用原 `matching_status` 表示原流程状态，另用 `ai_stage` 与 `pending_ai_review_count` 表示 AI 进度；不得把待确认冒充已审核完成。
- 若沿用原带风险下载，必须明显标记待复核/待重算，并保留原报告结论口径；不能以新状态绕过已有下载与成果质量门禁。

## 4. 建议数据契约

### Run 快照

`schema_version`、`task_id`、`run_id`、`input_sha256`、`artifact_version`、`requested_mode`、`effective_mode`、`skill_snapshot_id`、`asset_hashes`、`model_config_snapshot`（不含密钥）、`prompt_version`、`parser_version`、`mode_reason`、`ai_stage`、`operation_revision`。

新交互式入口显式传 `matching_mode=ai_enhanced`。旧任务/旧 API 缺字段维持机械兼容，机器人等未升级入口通过原路径或显式参数保持机械。本规则在前后端和任务恢复处统一，不能让缺省处理散落在多个组件。

### 来源与标准化记录

`SourceCell`：输入哈希、sheet、cell/range、原始文本、公式文本、缓存值状态。

`SourceRecord`：稳定记录 ID、源行集合、原字段、章节/备注作用域、排除原因。

`ProposedRecord`：目标字段/要素、来源 ID、推断性质、缺失/冲突项、待确认状态、目标模板行 ID。

`MappingPlan`：块范围、表头范围、列映射、声明式上下文引用、覆盖清单、模型/人工来源与版本。

只能引用实际读取过的来源 ID；拒绝越界 sheet/行、未知字段、重叠冲突、跳过未解释业务行、未知枚举和超出上限的响应。模型不得改变 read-only 的原始值。普通文本中的指令仅是资料内容；不跟随其中链接、不执行其中公式或命令。

### 候选、建议与确认

`CandidateSnapshot`：稳定候选 ID、目标字段、来源资产及哈希、行/规则 ID、原值、单位、适用条件、来源层级、出处是否完整。原值由服务器读取，不由模型回填。

`SemanticProposal`：提案 ID、输入/输出版本、记录 ID、目标字段、候选集哈希、选中候选 ID 或空、支持证据 ID、排除差异、缺失条件、结果枚举。

`Confirmation`：提案 ID、候选 ID、字段、预期成果版本、预期旧值、确认人和备注、幂等键。

服务端确认顺序：取得任务写锁 → 验证 Run/提案版本 → 检查当前单元格/人工修改 → 重新核验资产与候选 → 检查已确认前提与单位 → 从资产读取数字 → 在输出副本写入 → 原子提交新成果及确认审计。失败不留下半写值或“已确认但无成果”的成功状态。

一项 AI 派生要素可能影响多个字段时，确认界面必须显式列出这些影响；一次确认不能悄悄批准未展示的系数。重复确认返回原结果；版本冲突返回明确冲突并刷新建议。

### 建议 API

保持原端点兼容；在现有任务 API 结构下实现等价的“读取 AI 状态/提案、确认映射、启动辨析、确认候选、取消、切换新 Run”。建议路径形态为 `/api/process/{job_id}/ai-matching/...`，具体以当前路由习惯为准。启动请求快速返回 operation ID，页面轮询真实持久化状态或复用现有进度机制，避免在单个请求中等待全部模型与人工操作。

确认端点仅接受服务器已生成的提案 ID，不接受任意资产路径、任意价格或跨 Task/Skill ID。服务端负责作用域校验，不依赖前端隐藏按钮。

## 5. 时限、并行与缓存

在 `config/project-default-settings.json` 增加命名空间 `aiMatching`；以下为初始工程建议，实施时类型校验并冻结到 Run：

| 配置 | 建议初值 | 说明 |
| --- | --- | --- |
| `defaultMode` | `ai_enhanced` | 仅升级后的交互式填价入口使用 |
| `requireSemanticConfirmation` | `true` | 首版不可通过普通 UI 关闭 |
| `fallbackMode` | `mechanical` | 自动降级，持久化原因 |
| `totalModelBudgetSeconds` | `60` | 一次 Run 常规两轮模型墙钟消耗总预算，排除人工暂停，含请求排队及重试 |
| `requestTimeoutSeconds` | `20` | 单次请求上限，实际取其与剩余预算的较小值 |
| `maxConcurrency` | `3` | 同一业务任务内独立模型块并发；全局专业任务并发仍为 1 |
| `maxTransientRetries` | `1` | 仅瞬时网络错误且预算足够时；401、非法结构与业务冲突不反复请求 |
| `maxRowsPerBlock` | `25` | 还需按输入/输出 token 预算再分块；不能按行数盲发 |
| `maxInputRows` | `500` | 首版完整扫描的业务行上限，超过明确提示未处理范围，不静默截取 |
| `maxCandidatesPerField` | `5` | 有限检索集合，先做硬过滤；候选召回不足另记为检索失败 |

还需实现工作表数量、单元格扫描数、解压后体积、单字段文本长度、输入与输出 token 的安全上限，以现有上传限制和实测为依据。限制应可解释，不能把格式化空白尾行当成大量业务数据。不要沿用通用 `max_tokens=1800` 处理任意大块后把截断当作成功。

两轮模型调用前后以单调时钟累计实际墙钟消耗；人工确认暂停不占模型预算，但 UI 的端到端统计包含人工时间。新客户端需支持真正的连接/读取超时与全阶段截止时间、资源清理和取消；仅外层 `wait_for` 超时而后台同步请求继续排队不算实现。

有限并行只用于独立块；不得把专业任务队列扩为多个并行任务。每块保留输入索引与完成状态，完成顺序不同也不能串行/错行写回。冻结操作版本，取消、切模式、重试或进程重启后旧响应只能被丢弃。

缓存保存已校验建议及完整版本键，不保存秘密，也不缓存“人工批准权”。同内容不同章节/单位/规则版本不能共享判断。第一次运行冷缓存与重复使用热缓存分开计时；缓存条目异常只失效该条。标准模板直接机械识别的结果标为机械，不制造一次模型调用。

## 6. 离线、恢复与成果一致性

| 故障点 | 行为 | 验证证据 |
| --- | --- | --- |
| 创建时无密钥/模型不可用 | 即时机械降级；异构输入需人工映射时明确提示 | 请求/实际模式、原因、未处理范围 |
| 结构理解失败或输出不合法 | 丢弃未确认计划，回到原读取能力 | 没有 AI 字段泄漏到引擎 |
| 部分辨析块失败 | 保留其他建议，失败块待复核；已确认结果不回滚 | 块级成功/失败数之和等于提交数 |
| 超时/取消/刷新 | 持久化状态；恢复只查询或重试未完成块 | 无重复模型任务、重复写值和幽灵完成 |
| 确认时输入/资产/人工值变化 | 拒绝旧提案，重新生成或人工处理 | 冲突原因、原成果完整 |
| 输出保存/重算失败 | 不发布半成品为成功版本；保留上次有效成果 | 文件可打开、版本和审计一致 |
| 新模块初始化异常/缓存损坏 | 显式机械选择仍可工作 | 机械入口不触碰模型依赖 |

实施时优先沿用现有存储和原子写回机制，新增 sidecar 可放在本 job 内，如 `ai-matching-state.json`、`ai-matching-proposals.json`、`ai-matching-audit.jsonl`。这些是运行状态与审计；不能把唯一人工确认记录当成可任意清理的缓存。具体迁移、恢复和备份方式在实现后记录。

阶段完成后继续下一阶段，不把“后端写完”“构建通过”“mock 全绿”作为整个目标的停止点。每阶段更新 `实施进度.md` 的需求状态、命令结果、证据路径、未解决问题及下一步。

若外部条件阻断真实调用，先完成所有独立可推进工作，准确记录未通过门禁。只有同一不可自行解决的阻塞连续三次目标推进仍存在且无独立工作可做，才按目标工具规则标记 blocked；不得以增加 token 预算、关闭测试或放宽阈值绕过。

## 8. 测试、基线保护与发布检查

### 最低执行清单

1. `python -m pytest backend/tests -v`；前端使用 `package.json` 已有测试命令并增加必要行为测试，执行 `npm run frontend:build`。
2. 使用 `python tools/verify_v31_task_acceptance.py` 的正确运行环境复用正式流程；增加双模式适配及缺失差异门禁时，保持原答案、原输入和已存在测试不变。隔离 runtime，避免测试污染生产台账。
3. 新建模块专项测试覆盖 PRD G1/G2，独立真实模型验收脚本同时产出结构化 JSON 和人可读摘要；mock 只能验证契约/故障，不能证明 AI 效果。
4. 对无模型/完整新模式使用相同题集和候选召回输入，标注数据来源、黄金答案、留出集和不确定口径，报告所有失败，不能只挑成功例。
5. 浏览器核对实际模型调用、确认/拒绝、离线、超时、模式切换、历史恢复、三字段写入与重算；检查标题/标签/正文/按钮/控件的 computed 字体以及关键布局前后截图。需要运行态验证时允许按项目规则启动/重启本地 8000/5174。
6. 绿色版依据 `docs/绿色版说明.md` 生成并启动验收；新增配置/代码/可信模板和 Skill Manifest 资产必须携带，安装依赖有变化才做对应锁文件更新。云包通过唯一构建器和 `check_cloud_release.py` 检查，不部署、不发送消息。
7. `python tools/check_prd_consistency.py --strict`、`python tools/trim_changelog.py`；确认交付门禁后更新软件版本、README、当前计划、模块状态和 CHANGELOG。

### 不得破坏的资产与提交方式

- 原 `.xlsx` 知识库、规则表、经验池、Word 模板、V3.1 输入答案都只读。基线不一致先诊断，不能改答案证明自己正确。
- 新 AI 分支优先新增模块。实施前的脏改动先记录路径及哈希，必要时在 `Codex-Temp/` 保存源码差异/副本，不自动备份整套 PRD、不得运行代码 zip 存档。禁止 `git reset --hard`、`git clean`、批量 checkout 或 `git add .`。
- 默认在该项目当前本地目录串行实施；用户现有未提交文件与未跟踪正式样例是基线的一部分。若改用 worktree，必须显式带入当前工作树状态和必需的非 Git 业务资产，并验证来源哈希；不能只从 HEAD 建空白工作树后再声称资料缺失。
- 只提交本任务新增与修改部分；共享文件原有修改不能混入本次提交。文档阶段提交不是代码实现基线；实施任务仍需重新记录工作树状态。
- 不改全局 AGENTS/config，不换端口、不接管云端机器人、不改其他项目。任何新增依赖、运行数据保留范围和未完成现场验收须写入交付说明。

## 9. 资料与命令依据
