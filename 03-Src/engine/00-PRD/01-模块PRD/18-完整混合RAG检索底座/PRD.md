## 当前实现摘要（v5.19.5）

- 两套模式真实并存：未传模式固定走 `classic`；用户在知识库选择器旁主动切换 `hybrid`，个人偏好仅保存在浏览器本地。
- 混合通道由统一知识块和元数据驱动，实际包含 BM25、结构化字段、`local-hash-embedding-v1` 向量召回、RRF 融合、权威等级 / 数字 / 编码 / 比例尺 / 单位硬门控和 `local-rule-rerank-v1` 可选重排。
- 索引写入 `Codex-Temp/runtime` 的 Git 忽略缓存；正式 Markdown、Excel、CSV、规则资产和已确认知识记忆仍是真源。运行请求不静默修复损坏索引，显式重建后再恢复能力。
- `/api/knowledge/search`、`/api/knowledge/ask` 增加请求模式、实际模式、通道、证据状态、降级原因和追踪；旧客户端不传 `retrieval_mode` 时保持经典路径。
- 四道预置演示题在检索 / 模型前旁路返回，响应实际模式固定为 `curated_demo`；混合切换不改变 AI 填价候选、三个数字、经验池、工作量抓取、报告计算和正式资料。

## 一、背景与问题

当前知识问答已经能够先拆分复杂问题，再对 Markdown、Excel、CSV、规则说明和结构化计价库执行本地检索，最后由大模型依据检索证据组织回答。现有方案稳定、轻量、容易解释，对清单编码、比例尺、`0.22` 等精确词尤其有效，但其召回主要依赖规则扩词和加权关键词：

- 用户换一种说法、使用近义表达或省略标准术语时，可能漏召回。
- 多知识库、多文档和长问题中的词频权重缺少标准 BM25 统计。
- 结构化表格、正式规则、自然语言说明目前共用较多手工评分逻辑，扩展成本逐步增加。
- 向量语义、词法精确命中和结构化字段命中尚未形成统一融合与重排机制。
- 当前标准题集能验证答案关键事实，但还需要 Recall@K、nDCG、误召回率、时延和降级率等检索指标。

P1 建设完整混合 RAG，不替换现有稳定方案，而是让两套模式长期并存、由用户自主选择，并通过同一标准题集决定新模式是否具备默认启用资格。

## 二、为什么是 P1，而不是立即替换

混合 RAG 有明确收益，也有真实缺点。下列风险必须进入设计、测试和验收，不能只写“召回更智能”。

| 缺点 / 风险 | 具体表现 | P1 控制措施 |
| --- | --- | --- |
| 架构复杂度上升 | 从单一评分扩展为多个索引、多个召回通道、融合和重排 | 保留经典检索；新能力按独立模块和 feature flag 接入 |
| 索引维护成本 | 文档变更后要同步更新词法索引、向量索引、元数据和版本签名 | 正式资料是真源，索引全部视为可重建缓存；提供增量更新、全量重建和一致性检查 |
| 运行资源增加 | 本地向量模型、向量索引和重排会占用 CPU、内存、磁盘，并增加绿色版体积 | 优先选择可离线、轻量、跨 Windows / Linux 的模型与运行库；在验收机记录真实资源数据 |
| 首次构建和问答时延 | 首次下载 / 建索引、冷启动和重排可能变慢 | 模型随包或受控安装；后台建索引；分阶段进度；超时自动降级经典检索 |
| 调参成本 | BM25、向量 TopK、融合参数和重排阈值可能对不同题型表现不同 | 先冻结题集和基线，再调参；参数集中配置并保留版本 |
| 语义误命中 | “意思相近”不等于“业务条件一致”，尤其容易混淆数字、编码、等级、比例尺和单位 | 数字 / 编码 / 比例尺 / 单位设为硬约束；结构化冲突时降低或淘汰候选 |
| 可解释性下降 | 向量相似度和重排分值不如关键词命中直观 | 返回通道命中、融合原因、正式性等级、冲突项和降级原因；普通用户只看简明摘要，调试模式可展开 |
| 正式性与相关性冲突 | 语义上更相关的经验资料可能排在正式标准之前 | 正式标准、项目规则、结构化计价库的权威优先级独立于相似度，融合后仍执行证据等级门控 |
| 依赖与发布风险 | 新依赖可能影响绿色版、云端发布、UOS 预案或离线运行 | 依赖选择必须通过构建、云端发布检查和离线启动回归；不得依赖外部向量 SaaS 才能运行 |
| 外部模型与数据治理 | 若调用外部 embedding / rerank 服务，可能暴露资料内容并产生费用 | P1 默认本地推理；任何外部服务必须单独配置、明确授权、脱敏、可关闭且不保存秘密到项目默认配置 |

结论：这些缺点不会否定混合 RAG，但决定了它应作为可切换、可评测、可降级的 P1 增强能力，而不是直接覆盖现有检索。

## 模块目标

1. 提升同义改写、口语问法、长问题和跨文档问题的召回能力。
2. 保住清单编码、数字、比例尺、单位、等级和正式条款等精确问题的稳定性。
3. 让用户可在“经典检索”和“混合 RAG”之间自主选择，并在回答中看到实际采用的模式。
4. 让每条回答仍能定位到真实来源、标题路径、表格行或规则卡片。
5. 新模式故障时自动降级，不阻断 Excel 填价、预警、报告、下载和经典知识问答。
6. 用标准题集和真实指标证明是否变好，不以“用了向量库”本身作为成功标准。

## 功能边界

- 不让大模型或向量相似度直接裁决 `基价 / 单价`、`实物工作费调整系数`、`技术工作费调整系数`。
- 不替换主填价的结构化匹配引擎，不改变经验池预警、工作量抓取和 Word 报告计算逻辑。
- 不把检索索引当作正式知识真源，不允许从索引反写正式资料、规则表、结构化计价库或经验池。
- 不把“混合 RAG”做成新的左侧一级菜单、第二个聊天窗口或与问问智算割裂的独立产品。
- 不因语义相近而放宽数字、编码、比例尺、单位、等级、项目范围和 Skill 范围的硬约束。
- 不自动把聊天内容写入正式知识库；知识记忆仍执行候选、审核、版本和撤销流程。
- P1 不强制接入外部向量数据库或外部 embedding 服务。

## 五、用户场景

| 场景 | 经典检索优势 | 混合 RAG 目标 |
| --- | --- | --- |
| 精确清单编码查询 | 编码命中稳定 | 不得退化；编码硬约束后融合 |
| `0.22`、`1:50000` 等数字问题 | 规则扩词和精确匹配有效 | 不得把相似数字、相邻比例尺当作同一条件 |
| “技术工作费怎么收”等口语问法 | 依赖现有扩词覆盖 | 通过语义召回补足未登记说法 |
| 多条件长问题 | 已先拆分业务问题和输出要求 | 在拆分后对业务子问题并行召回、统一融合 |
| 跨标准资料与项目规则解释 | 需要多个片段共同支持 | 找到互补证据，并按正式性和覆盖度重排 |
| 无依据问题 | 零证据模型兜底 | 维持低误召回，不因向量相近伪造知识库命中；明确转普通大模型且来源为空 |

## 六、双模式切换交互

### 6.1 按钮位置与形态

- 在问问智算输入区的现有“选择知识库”控件旁增加紧凑分段切换按钮。
- 两个选项固定命名为：`经典检索`、`混合 RAG`。
- 默认选中 `经典检索`，避免 P1 上线即改变当前稳定行为。
- 仅在知识库问答场景显示；普通闲聊、批量匹配、经验池预警、下载等动作模式不显示或不生效。
- Dock 小窗口和宽屏智算助手使用同一状态；窄窗口允许按钮独占一行，不能挤压输入框或知识库选择器。
- 使用现有大尾巴 Shadcn UI 令牌、苹方字号和 Lucide 图标，不使用渐变、高饱和警示色或第二套组件体系。

### 6.2 状态与持久化

- 项目默认值写入 `config/project-default-settings.json`，建议新增 `knowledgeRetrieval.defaultMode = "classic"`。
- 用户切换只保存为本浏览器偏好；不修改项目默认配置，不影响其他用户。
- 每次发送时把检索模式冻结到该条消息。之后切换模式不得改变历史回答的标签和依据。
- 四道预置演示题继续在检索前返回人工审核答案；切换按钮不应让预置题假装执行混合 RAG。
- AI填价候选仍由结构化程序排序。P1 首版切换按钮只控制问问智算知识问答，不控制 AI填价数字候选。

### 6.3 用户反馈

- 回答依据摘要中显示 `检索模式：经典检索` 或 `检索模式：混合 RAG`。
- 混合 RAG 降级时显示 `混合 RAG 暂不可用，本次已自动使用经典检索`，并提供可展开原因。
- 等待态按真实阶段显示：解析问题、词法检索、结构化检索、语义检索、融合重排、核验证据、组织回答。
- 进度条只能反映阶段推进，不伪装模型内部真实百分比；完成前不提前跳到 90%。

### 6.4 可用性与兼容

- 后端未声明混合 RAG 可用时，按钮显示禁用态并说明“索引尚未就绪”，不得点击后静默走经典模式。
- 键盘可切换，具有清楚的 `aria-label`、选中状态和焦点样式。
- 旧客户端不传模式时必须继续走经典检索。

## 七、检索总体架构

```text
用户问题
  → 强制知识库 / 自动知识库路由
  → 三段式问题拆分
  → 检索模式选择
      ├─ 经典检索：现有扩词 + 加权关键词 + 结构化偏好
      └─ 混合 RAG
          ├─ 查询规范化与硬约束提取
          ├─ BM25 / 词法召回
          ├─ 结构化字段召回
          ├─ 向量语义召回
          ├─ 去重与多路结果融合
          ├─ 权威等级、字段冲突和适用范围门控
          ├─ 可选轻量重排
          └─ 证据充分性判断
  → 有证据：受约束大模型组织回答
  → 零证据：明确提示“已自动转为大模型回答”，输出无知识库来源的通用模型兜底
  → 来源、模式、通道、分值与降级记录
```

## 八、混合 RAG 详细流程

### 8.1 查询理解

继续复用现有三段式拆分：

```text
业务检索问题
回答与展示要求
补充说明要求
```

只有业务检索问题进入召回。随后确定性提取：

- 清单编码、序号、条款号。
- 数字、百分比、费率、`0.22` 等系数。
- 比例尺、管径、单位、等级、复杂程度。
- 表号、业务模块、项目 / Skill 范围、选中的知识库。
- “只回答”“用表格”“输出图表”等展示要求保留给回答组织，不作为高权重检索词。

大模型可以在后续版本辅助生成语义改写，但首版核心约束提取必须可测试、可复现；大模型改写失败不能阻断检索。

### 8.2 召回通道

| 通道 | 作用 | 主要数据 | 关键边界 |
| --- | --- | --- | --- |
| BM25 / 词法召回 | 标准词频、稀有词、精确短语和文档长度归一 | Markdown、Excel / CSV 文本块、规则说明 | 保留数字和编码，不做模糊替换 |
| 结构化召回 | 按要素、单位、编码、比例尺、等级和表号精确过滤 | 结构化计价库、规则卡、表格行 | 字段冲突时不能仅靠高相似度入选 |
| 向量语义召回 | 覆盖同义改写、口语表达和跨措辞语义 | 同一知识块的本地向量 | 仅提供相关性候选，不代表正式结论 |
| 定向规则召回 | 对 `0.22`、技术工作费、附加调整系数等现有高价值规则保持稳定路由 | 项目规则、正式标准和功能知识卡 | 不因引入向量而删除现有可靠规则 |

### 8.3 融合与重排

- 不直接把不同通道的原始分值相加，因为 BM25、向量相似度和结构化分值量纲不同。
- 首选使用基于排名的融合方法，例如 RRF；具体参数以标准题集调优并进入集中配置。
- 融合后再应用业务门控：正式性等级、知识库范围、Skill 范围、项目范围、数字 / 编码 / 单位 / 比例尺一致性。
- 结构化精确命中和正式规则命中可增加可解释加权；明确字段冲突必须降权或淘汰。
- 可选重排器只能重排已召回候选，不得生成新证据；超时立即使用融合结果。
- 相同来源、相同标题路径和高度重叠内容要去重，保留能覆盖不同事实的互补证据。

### 8.4 证据门控

回答前必须判定：

1. 候选是否来自本次选中的知识库和当前 Skill / 项目范围。
2. 关键数字、编码、比例尺、单位和等级是否一致。
3. 是否至少存在一条能够直接支持核心结论的证据。
4. 多条正式依据是否互相冲突。
5. 项目记忆是否与正式标准冲突或已疑似失效。

零证据时不再返回固定拒答，而是自动转入普通大模型兜底：

```text
已自动转为大模型回答

<普通大模型回答>

提示：本回答未检索到本地知识库明确依据，仅供一般参考；涉及价格、系数、正式标准或项目口径时，请以项目规则和人工复核为准。
```

兜底模型不得声称回答来自知识库，不得生成虚假来源、项目内部事实、价格、系数、条款编号或标准出处。证据冲突不等同于零证据，仍应并列展示冲突并交人工复核。

若存在冲突，必须把冲突来源并列展示并提示人工复核，不得让重排器替用户裁决正式口径。

## 九、数据与索引设计

### 9.1 真源与缓存

正式资料、结构化计价库、规则表和已确认知识记忆仍是真源。以下均为 Git 忽略、可重建的运行缓存：

- 现有经典检索索引。
- BM25 / 词法索引。
- 向量索引和文档向量。
- 文档元数据、分块版本、模型版本和内容签名。
- 融合 / 重排调试记录的有限审计数据。

知识记忆 SQLite 是受治理运行数据，不是可随意删除的索引缓存；两者必须继续区分。

### 9.2 分块与元数据

每个知识块至少保存：

```text
chunk_id
source_file
source_type
library_id
skill_id / skill_version
project_key（如适用）
title_path
sheet_name / row_number（如适用）
module
authority_level
content_hash
updated_at
embedding_model_version
```

- Markdown 优先按标题层级和段落分块。
- Excel / CSV 优先按表头 + 单行记录生成结构化块，避免把多行价格混在一个语义块中。
- 规则卡保留规则 ID、适用条件、例外和正式性等级。
- 分块策略、模型版本或真源内容变化后，对受影响块增量重建；无法确认一致性时执行全量重建。

### 9.3 本地模型与依赖

- v5.19.5 首版采用项目内置、Python 标准库实现的 `local-hash-embedding-v1`（384 维确定性向量）和 `local-rule-rerank-v1`，不下载模型、不接外部向量 / 重排服务，新增第三方依赖为 0。
- 许可证 / 包体：无第三方模型或模型文件，新增模型资产 0 MB；实现随项目代码分发，继续受项目既有许可证和发布清单约束。
- 运行资源实测（2026-08-06，4014 个知识块，Windows 本机）：首次构建 62,234.200 ms，混合索引 67,026,858 bytes（约 63.922 MiB），Python `tracemalloc` 峰值 556.625 MiB；热检索 5 次 P95 1,331.252 ms，满足 1.5 秒目标但保留 classic 默认。
- 模型与索引均带版本 / 真源签名；真源变化或版本变化后索引标为 stale 并受控重建。运行秘密、外部服务地址和个人偏好不写入索引或项目默认配置。


未传 `retrieval_mode` 时固定为 `classic`。

### 10.2 响应

实际新增：

```json
{
  "requested_retrieval_mode": "hybrid",
  "retrieval_mode_used": "hybrid",
  "actual_retrieval_mode": "hybrid",
  "retrieval_channels": {},
  "evidence_status": "sufficient",
  "degradation_reason": null,
  "degradation_reasons": [],
  "retrieval_trace": {
    "query_parts": {},
    "channel_hit_counts": {},
    "evidence_status": "sufficient | insufficient | conflict"
  }
}
```

- 普通界面只显示模式、来源和必要的降级说明。
- 现有“大模型调试模式”可展开通道命中、融合排名、重排分和冲突原因。
- API 不返回本机绝对路径、密钥、模型下载票据或未授权项目内容。

### 10.3 能力探测

知识库列表响应返回混合 RAG 是否可用、索引状态、模型版本、维度、离线能力和重排超时配置。前端依据真实状态启用按钮，不通过静态常量假装可用；当前索引损坏或未就绪时禁用 hybrid，接口请求仍可按降级规则回到 classic。

## 十二、降级与回滚

| 故障 | 系统行为 |
| --- | --- |
| 向量模型未就绪 | 能力探测返回不可用并禁用混合 RAG 按钮；经典检索继续可用 |
| 向量索引缺失或损坏 | 能力探测返回未就绪 / invalid；本次请求记录原因并自动降级经典检索，显式重建后恢复 hybrid |
| 向量召回超时 | 使用 BM25 + 结构化候选；仍不足时降级经典检索 |
| 重排超时 / 异常 | 使用融合排名，不阻断回答 |
| 混合零证据 | 明确标识后自动转普通大模型兜底；不附知识库来源，不允许冒充知识库或专业裁决 |
| 大模型不可用 | hybrid 保留检索结果和依据摘要，返回 evidence fallback 与降级原因；classic 保持既有错误兼容 |
| 新模式指标退化 | feature flag 关闭混合 RAG，经典检索保持默认 |

任何降级都不得改变三个数字、原始 Excel、输出副本、规则资产或知识真源。

## 十三、评测集与指标

### 13.1 题集分层

在现有语义回归基础上扩充并人工标注黄金证据：

- 精确题：清单编码、表号、条款号、比例尺、管径、单位、费率。
- 简单解释题：单一概念或规则。
- 复杂约束题：业务检索问题 + 表格 / 图表要求 + 原理说明。
- 语义改写题：同一问题的口语、缩写、倒装和近义表达。
- 跨文档题：需要两条以上互补证据。
- 冲突题：正式标准与项目记忆 / 历史案例冲突。
- 无依据题：与业务相似但知识库没有正式答案。

必须保留现有 `0.22` 表2例外、表3系数、清单编码、数字化费率、走向图比例尺、过路过桥费和无依据题，不得为了让新模式分数更高而删题。

### 13.2 验收指标

在声明硬件、知识源版本和索引版本的验收环境中：

| 指标 | 最低口径 |
| --- | --- |
| 经典模式回归 | 现有标准题关键事实和来源定位全部不退化 |
| 精确数字 / 编码保护集 | 正确黄金证据 Recall@5 = 100% |
| 混合模式总体召回 | 黄金证据 Recall@5 ≥ 95% |
| 排序质量 | nDCG@10 相对经典模式有可复现提升；若无提升，不得设为默认 |
| 引用准确率 | 回答核心事实可被展示证据直接支持的比例 ≥ 95% |
| 无依据控制 | 零证据题必须保持 `evidence_found=false`、来源为空并显示“已自动转为大模型回答”；兜底不得伪造来源或专业裁决 |
| 模式一致性 | 请求模式、实际模式、降级原因和界面标签完全一致 |
| 检索时延 | 热索引本地检索 P95 目标 ≤ 1.5 秒；超时按配置降级并记录 |
| 稳定性 | 向量、重排或大模型任一组件故障时，经典检索与专业主流程仍可用 |

“混合模式更好”必须由上述指标和失败案例清单共同证明，不接受只展示少量成功问答。

## 十八、已确认的技术决策

1. embedding 采用项目内置 `local-hash-embedding-v1`，384 维、无模型下载、无新增第三方依赖；新增模型资产 0 MB，无额外第三方许可证。
2. 索引采用 UTF-8 JSON 可重建缓存，Windows / Linux 均由 Python 标准库路径和 JSON 读写处理；正式发布包不把运行索引当知识真源。
3. 重排采用 `local-rule-rerank-v1`，默认开启、超时 180 ms；超时或异常使用融合结果，不改变证据来源。
4. 验收机资源实测已写入 9.3：索引约 63.9 MiB、首次构建约 62.2 秒、Python 追踪峰值约 556.6 MiB、热检索 P95 1.331 秒；因此 hybrid 继续手动可选，classic 继续默认。
5. 不允许外部 embedding / rerank 服务；有证据时大模型只做受约束表达，零证据时可转普通大模型提供一般性回答，但必须明确无知识库依据，不能生成新证据、裁决冲突或生成项目价格与系数。

## 十九、完成定义

只有同时满足以下条件，才可把本模块从 `[待开发]` 改为 `[已完成]`：

1. 两套检索模式真实并存，默认经典检索，用户可在大小窗口自主切换。
2. 混合模式真实包含词法、结构化、向量召回、融合、门控和可选重排，不是更名后的原评分函数。
3. 请求模式、实际模式、降级原因、引用来源和调试追踪一致。
4. 现有标准题和预置演示题全部不退化，新模式达到本 PRD 指标。
5. 向量 / 重排 / 大模型故障均能降级，专业主流程不受影响。
6. 自动化测试、前端构建、浏览器验收和相关发布检查通过。
7. README、当前版本计划、模块 PRD、CHANGELOG 和版本号按实际实现同步。
8. 完成独立本地 Git 存档；未经用户明确要求不自动推送云端。
