# Task 任务对象与执行轨迹 PRD

## 模块目标

把 `Task` 从分散在上传任务、对话任务、项目运行、飞书 / WeAct 协同任务和知识候选中的技术编号，提升为用户可感知、跨模块一致、可追溯的一等业务对象。

本模块不新建一个只展示英文概念的“Task 页面”，也不重做现有任务库。它以一条真实业务任务为主线，把任务目标、输入、专业 Skill、实际调用的 Tool、执行阶段、人工复核、成果版本和 Experience 血缘连接起来，让用户和评委能够在系统中直接看到：

> **一项 Task，调用一套专业 Skill，组合一组可信 Tool，经过人工复核形成正式成果，再沉淀为可治理的 Experience。**

P0 的重点是“统一身份、显性呈现、真实追溯”，不是建设通用流程引擎。现有三个数字匹配、经验池预警、报告生成、多人复核和知识治理仍由各自专业模块裁决。

## 为什么现在做

当前系统已经具备 Task 的主要组成部分，但尚未形成一个对用户可见的完整对象：

- `TaskEnvelope` 已承载外部系统任务、项目、Skill、人员、截止时间和输入模板。
- `SkillRuntimeContext` 已在任务创建时冻结 Skill 版本、计价库、规则、风险、知识和报告模板。
- 项目台账已保存 `ProjectRun / Job`、成果引用、文件版本和复核轮次。
- 智能协同已保存任务派发、领取、成果回传、多人复核、评论、退回和完成状态。
- 可信经验闭环已保存项目、任务、Skill、成果哈希、知识候选、项目胶囊和跨项目复用血缘。

问题不是缺少更多任务表，而是这些信息分散在不同入口和运行库中，用户看不到同一项任务如何从“收到任务”走到“形成成果并沉淀经验”。因此 P0 应优先建立兼容映射和统一只读视图，再决定后续是否收敛底层存储。

## 定位与优先级

- 优先级：**P0，比赛主线显性化能力**。
- 用户侧主名称：**任务**；`Task` 只作为方法论辅助标签，不要求普通用户理解英文术语。
- 导航位置：**不新增左侧一级菜单**。
- 主要呈现位置：智算助手、填价工作台、结果预览、Word 报告、智能协同和项目看板。
- 实施原则：复用现有任务、Skill、项目、协同、成果和经验数据；不复制业务状态，不以模型文本模拟执行过程。
- 竞赛价值：让“Task → Skill → Tool → 人工复核 → 成果 → Experience”通过同一条真实执行轨迹可见，既服务创新表达，也补强作品完整性证明。

## 业务对象层级

系统后续统一采用以下层级，避免“项目、任务、运行、版本”相互混用：

```text
Project 项目
└─ Task 业务任务：一个稳定的业务目标
   ├─ Run 技术运行：一次处理尝试、重试或重算
   ├─ ReviewRound 复核轮次：一次多人复核与退回循环
   ├─ ArtifactVersion 成果版本：Excel / Word / JSON 等正式或过程成果
   ├─ TaskEvent 执行事件：真实阶段、时间、来源和结果
   └─ ExperienceLineage 经验血缘：候选、确认、提升、命中、撤销与失效
```

### 1. Project 项目

项目是一个持续业务容器，可以包含多项 Task。项目名称相同不等于同一个项目；项目归属继续以可靠 `project_id` 为准。

### 2. Task 业务任务

Task 表示一项有明确目标、输入、专业能力、预期成果和完成条件的业务工作。例如：

> 完成“某项目可行性研究勘察测量最高投标限价编制”，输出可复核 Excel 与 Word 报告，并完成多人复核。

Task 在以下情况保持不变：

- 同一任务失败后重试。
- 同一任务重新执行匹配或风险检查。
- 同一成果刷新预览或重新下载。
- 同一任务退回修改并进入下一复核轮次。

以下情况应新建 Task：

- 用户明确“新建任务 / 重新开始”，且业务目标或输入对象已经变化。
- 更换专业 Skill；既有 Task 的 Skill 快照不得被改写。
- 上游系统传入新的可靠 `source_task_id`。
- 原任务已完成后，用户启动一个新的独立业务目标，而不是生成同任务新版本。

### 3. Run 技术运行

Run 是 Task 下的一次技术执行，不直接等于业务任务。现有网页 `job_id` 和项目台账 `run_id` 优先映射到这一层。重试或重算可以生成新 Run，也可以按现有兼容策略更新同一 Run，但不得因此增加项目数或 Task 数。

### 4. ReviewRound 与 ArtifactVersion

退回再提交沿用同一 Task，复核轮次递增；每轮应绑定明确成果快照与哈希。报告刷新、同版本再次下载不生成新成果版本；内容发生变化后才生成新版本并保留旧版只读引用。

### 5. ExperienceLineage

Experience 不是 Task 的聊天摘要，而是从真实人工修改、AI填价确认、多人复核意见、风险处置和结项事件中形成的受治理候选。候选、已确认、已提升、已撤销和疑似失效必须明确区分。

## 现有对象兼容映射

| 现有对象 | 在统一模型中的位置 | P0 处理方式 |
| --- | --- | --- |
| `TaskEnvelope` | 外部来源的 Task 定义输入 | 保留业务幂等键和原字段，写入统一 Task 身份与定义快照 |
| `SkillRuntimeContext` | Task 的不可变专业能力快照 | 原样引用 Skill ID、版本、Manifest 哈希和资产清单，不复制专业资产 |
| 网页 `job_id` | Task 下的技术 Run 标识 | 建立 `task_id ↔ job_id ↔ run_id` 关联；兼容期允许以现有 job 生成稳定 Task 映射 |
| 项目台账 `ProjectRun` | Task 的运行、统计和成果引用 | 继续承载现有运行指标；项目看板按 Task 视图聚合，不删除历史 Run 口径 |
| 智能协同任务 | Task 的派发、领取、复核和组织协同状态 | 协同库继续作为协同状态真相；统一 Task 只引用并规范展示，不建立第二套可编辑审核状态 |
| `project_artifacts` 与运行目录成果 | ArtifactVersion | 继续使用安全下载引用和文件哈希，不向前端暴露绝对路径 |
| `trusted_experience_events / capsules` | ExperienceLineage | 通过 `task_id / project_id / artifact hash` 关联候选、胶囊、命中和撤销记录 |

## Task 定义快照

P0 的任务定义至少包含以下字段：

| 字段组 | 必要内容 | 规则 |
| --- | --- | --- |
| 身份 | `task_id`、任务名称、`project_id`、项目名称 | `task_id` 稳定唯一；没有可靠项目归属时必须标记“待归类”，不能按文件名猜项目 |
| 来源 | 网页、智算助手、外部系统、普通飞书、企业 WeAct；`source_system / source_task_id / event_id` | 外部任务继续使用来源幂等键；内部绝对路径、平台密钥和用户 ID 不回显 |
| 目标 | 用户要完成什么、预期业务结果、必要补充说明 | AI 可从明确指令预填，歧义项需用户确认；不得由模型补造项目事实 |
| 输入 | 文件名、文件类型、受控文件引用、文件哈希、输入版本 | 原始文件只读；前端不提交任意服务器路径 |
| Skill | `skill_id`、中文名称、版本、Manifest 哈希、运行时能力摘要 | 创建后锁定；切换 Skill 必须新建 Task |
| 预期成果 | Excel、Word、JSON、风险清单等输出契约 | 只展示当前 Skill 实际支持的成果，不把远期能力显示为可执行 |
| 完成条件 | 必须完成的自动阶段、人工闸门和异常降级条件 | 简单任务允许“编制—多人复核”；不强制增加审批人 |
| 责任信息 | 编制人、复核人、截止时间、投递通道 | 仅协同任务必填；继续遵守 1—10 人、明确选择和平台可达性约束 |
| 时间与版本 | 创建、更新、完成时间；当前 Run、成果版本、复核轮次 | 时间来自后端真实事件，不使用前端假时间推进 |

## 状态与执行阶段

### 业务状态

P0 对现有多套状态做展示层规范化，不立即破坏性改写旧表：

| 规范状态 | 含义 | 典型来源状态 |
| --- | --- | --- |
| 待开始 | Task 已建立，但输入或必要确认未完成 | 待派发、待领取、待收件、材料待补充 |
| 处理中 | 专业处理已经真实开始 | 排队、识别中、匹配中、预警中、报告生成中 |
| 待人工复核 | 自动处理完成，存在需要人工确认的项目 | 待复核、待处理、候选待确认 |
| 协同复核中 | 成果已冻结并进入一名或多名复核人的当前轮次 | 待复核、复核中 |
| 已退回 | 当前复核轮次被退回，等待修改和新版本 | 退回修改 |
| 已完成 | 完成条件满足，真实成果可用 | 复核完成、已归档、处理完成 |
| 失败 | 当前阶段发生不可继续错误 | 失败 |
| 已取消 | 用户或有权限人员终止任务 | 已取消 |

规范状态只用于跨模块显示与查询。各专业模块仍保存并校验自己的细粒度状态，统一层不得反向覆盖协同审核结论或专业处理结果。

### 执行阶段

执行轨迹按任务实际启用的阶段展示：

```text
任务已定义
→ Skill 已冻结
→ 输入已接收
→ 结构已识别
→ 规则已执行
→ 风险已检查
→ 人工已复核
→ 成果已生成
→ 协同已完成
→ Experience 已治理
```

- 没有调用的阶段标记为“不适用”，不得标绿。
- 正在运行的阶段展示后端真实状态和最近更新时间，不用固定百分比冒充进度。
- 失败阶段显示脱敏错误、可重试动作或“转人工”，此前已成功阶段保留。
- `Experience 已治理` 只有产生候选并完成相应人工治理时才可完成；没有候选时显示“未形成候选”，不能因此阻止业务 Task 完成。

## P0 页面与交互方案

### 1. 左侧导航

不新增“Task 中心”或“任务管理”一级入口。Task 是贯穿现有业务页面的上下文，不是与填价、报告、协同并列的一项孤立功能。

### 2. 当前任务条

在智算助手和专业工作区页头下方使用同一紧凑组件，建议包含：

```text
当前任务  TASK-…  某项目勘察测量最高投标限价编制
来源：网页 / WeAct   Skill：勘察测量 v1.0.0（已锁定）
状态：协同复核中    第 2 轮    成果：Excel v2 / Word v2
[查看任务] [返回当前阶段] [查看成果]
```

- 宽屏显示一行主信息加一行辅助信息，避免大卡片挤压表格。
- 右侧问问智算 Dock 只显示“任务名称 + 状态 + 详情”摘要，点击后在主工作区展开。
- 结果预览和 Word 报告继续以成果为主，只在顶部工具条显示同一 Task 身份和版本。
- 当前任务条使用真实数据；空状态不显示 KPI、进度或伪造编号。

### 3. 任务详情抽屉

“查看任务”打开右侧抽屉或现有详情面板，按以下顺序组织：

1. 任务身份与目标。
2. 当前状态、责任人和截止时间。
3. 已冻结的专业 Skill。
4. 执行轨迹。
5. 实际调用的 Tool 与证据摘要。
6. 人工复核和协同轮次。
7. 成果版本。
8. Experience 血缘。

详情抽屉只提供安全跳转、下载和既有允许动作；不得在统一层重新实现逐行改值、审核通过 / 退回或知识确认。

### 4. 实际 Tool 展示

Tool 不单独建设“工具商店”。执行轨迹中只展示本 Task 实际调用且有运行证据的能力，例如：

- Excel 结构识别。
- 勘察测量确定性填价引擎。
- 结构化风险检查与经验池预警。
- 知识检索与有证据解释。
- Word 报告生成与 DOCX 预览。
- 飞书 / WeAct 投递与多人复核。

用户默认看到中文业务名称；展开技术详情后才能看到处理器 ID、规则 / 模板版本、开始结束时间和结果摘要。模型“准备回答”不得冒充 Tool 已执行。

### 5. 各模块如何体现同一 Task

| 模块 | Task 呈现 | 继续由谁负责业务真相 |
| --- | --- | --- |
| 智算助手 | 发起任务、确认定义、查看计划、阶段和成果 | 现有会话状态与专业 API |
| 问问智算 Dock | 当前任务摘要、行级上下文、证据解释 | 现有问答与知识检索 |
| 填价工作台 | 当前任务条、开始处理、字段映射、返回看板 | 现有上传与处理链路 |
| 结果预览 | Task / Run / 成果版本、待复核数和去处理 | 现有预览、人工修改与下载 API |
| Word 报告 | Task / 成果版本、生成时间和下载 | 现有报告生成与 File Viewer |
| 智能协同 | 同一任务的派发、领取、复核轮次和意见 | 现有协同状态机与身份校验 |
| 项目看板 | 项目下 Task 列表、详情轨迹、成果和经验摘要 | 现有项目台账与聚合 API |
| 知识记忆 | 来源 Task、项目、Skill、成果哈希和治理状态 | 现有知识治理状态机 |

## 关键交互流程

### 流程 A：网页或智算助手发起

```text
选择 Skill / 上传 Excel / 输入目标
→ 形成任务定义摘要
→ 用户执行“开始处理”
→ 创建稳定 Task 身份并冻结 Skill
→ 调用既有专业 API 产生 Run 和阶段事件
→ 需要人工处理时跳转原专业页面
→ 生成真实 Excel / Word 成果
→ 可选发给同事复核
→ 记录复核轮次和结论
→ 形成受治理的 Experience 候选或明确“未形成候选”
```

如果用户只是问知识问题，不自动创建业务 Task；只有上传文件并明确开始专业处理、外部任务进入或用户显式“新建任务”时创建 Task。

### 流程 B：外部系统 / 飞书 / WeAct 发起

```text
接收并校验 TaskEnvelope
→ 按来源幂等键创建或找到 Task
→ 冻结 Skill、模板、编制人和复核人
→ 投递待填写表格与任务卡
→ 编制人领取并提交成果
→ 专业处理与多人复核持续写入同一 Task 轨迹
→ 全员通过后形成完成版成果
→ 项目看板、网页和协同端看到同一状态
```

飞书 / WeAct 只负责触达、提醒、安全跳转和经验证的轻量操作；网页与后端专业服务仍是任务、成果版本和审核结论的业务真相。

### 流程 C：退回、重试与继续处理

- 技术失败重试：保留 Task，新增或更新 Run，失败事件不可删除。
- 多人复核退回：保留 Task，复核轮次递增，绑定新成果版本。
- 历史项目继续处理：用户明确选择旧 Task 时恢复；要开展新目标时新建 Task。
- 更换 Skill：必须新建 Task，并保留原 Task 只读历史。

## 数据与接口建议

### 1. 数据策略

P0 推荐先建设“统一身份登记 + 事件化只读聚合”，不做一次性大迁移：

- 统一任务登记只负责 `task_id`、定义快照和旧编号映射。
- 项目台账继续负责项目、Run、统计和成果引用。
- 专业任务库继续负责处理状态与结果。
- 智能协同库继续负责派发、人员、复核和卡片回调状态。
- 知识记忆库继续负责候选、确认、提升、撤销和失效。
- Task 详情服务按关联 ID 聚合为只读视图；任何写操作仍路由到原责任模块。

建议的最小新增对象：

```text
BusinessTask
- task_id
- project_id
- source_type / source_reference
- task_name / objective
- skill_snapshot_json
- input_contract_json / output_contract_json
- success_criteria_json / human_gates_json
- created_at / updated_at / completed_at

TaskLink
- task_id
- job_id / run_id / external_task_id / source_task_id
- link_type / created_at

TaskEvent
- event_id / idempotency_key
- task_id / run_id / artifact_version / review_round
- stage / status / actor_type / source_module
- summary / safe_reference
- occurred_at
```

`TaskEvent` 只能记录已发生的真实事实；详情接口可缓存聚合结果，但缓存不能成为专业状态的第二真相。

### 2. API 建议

| API | 用途 | 边界 |
| --- | --- | --- |
| `GET /api/tasks/{task_id}` | 返回统一任务定义、当前状态、关联对象和安全操作入口 | 不返回密钥、绝对路径、平台 ID、文件 Key |
| `GET /api/tasks/{task_id}/timeline` | 返回按时间排序的真实阶段事件 | 事件不可由前端补造；缺失阶段明确未知或未运行 |
| `GET /api/projects/{project_id}/tasks` | 返回项目下业务 Task 列表 | 不把每次 Run 当作新 Task |
| `POST /api/tasks` | 智算助手 / 网页显式创建任务 | 校验 Skill 与输入；外部任务继续优先走 `TaskEnvelope` 幂等入口 |
| `POST /api/tasks/{task_id}/links/reconcile` | 管理员或受控回填建立旧任务映射 | 幂等、可审计；不得按同名文件自动合并 |

接口命名可在实现时结合现有路由收口，但必须守住“同一 Task 身份、原模块负责写操作、聚合层只读”的原则。

## UI 规范

- 严格复用 `00-PRD/03-整体UI设计PRD.md` 和 `00-PRD/03-UI设计规范.md`，不得新建平行主题。
- 当前任务条、执行轨迹和详情抽屉使用纯白背景、`1px` 浅边框、低圆角、无常驻阴影、无渐变，不做卡片套娃。
- 使用自托管苹方和 `--dws-*` token；页面标题 `28px`、模块标题 `20px`、面板标题 `16px`、正文 `14px`、导航 / 控件 / 按钮 `13px`、辅助说明 `12px`，可见业务文字不得小于 `12px`。
- 当前任务条高度保持紧凑，优先保护 Excel 表格和 DOCX 预览可用面积；执行轨迹在抽屉或详情区展开，不在每个页面常驻一条大型流程图。
- 状态色服从现有语义色：处理中用蓝、待人工用橙、成功用绿、失败用红、未运行 / 不适用用中性灰；颜色不能成为唯一信息载体。
- 同层级任务名称、状态徽标、阶段名称、时间、责任人和按钮必须字号、字重、行高一致。
- 窄屏时折叠为“任务名称 + 状态 + 查看详情”；不得出现横向溢出或遮挡右侧 Dock。
- 支持键盘聚焦、`aria-label`、减少动态效果；执行轨迹动效只作为真实状态变化反馈，不得循环表演。

## 竞赛展示方案

Task 不额外占用一段“概念讲解页”，而作为 8 分钟主线中的可视化骨架：

1. 展示一个真实 Task 从外部信号或智算助手进入，任务定义中可见项目、目标和输入。
2. 展示专业 Skill 已冻结，说明“换专业不是换一张库，而是换完整能力包”。
3. 执行过程中只点开 1—2 个关键节点，证明结构识别、确定性规则和风险检查由真实 Tool 完成。
4. 从同一 Task 跳到结果预览与多人复核，展示人工闸门和真实意见。
5. 返回 Task 详情查看 Excel / Word 成果版本，以及由本任务形成的知识候选 / 项目胶囊。
6. 用一句话收束：任务不是页面标签，而是把 Skill、Tool、人、成果和 Experience 串成可验证闭环的业务载体。

展示中的 Task 编号、时间、状态、风险数量、成果和经验状态全部来自真实运行。现场故障时可以展示预先跑通的只读真实任务记录，但不得用前端假动画伪造任务已完成。

## 验收口径

### P0 产品验收

- 网页 / 智算助手发起和外部协同发起至少各跑通一项真实 Task，二者都能生成稳定任务身份和定义快照。
- 同一 Task 在智算助手、填价工作台、结果预览、Word 报告、项目详情和智能协同中显示相同任务编号、项目和 Skill 版本。
- Skill 快照创建后不可被全局默认 Skill 或当前选择漂移改写；更换 Skill 必须创建新 Task。
- 重试、重算、报告刷新、下载和页面切换不重复创建 Task；退回再提交保持同一 Task 并增加复核轮次和成果版本。
- 执行轨迹中的完成节点都有后端真实事件、时间和来源；未执行、不适用、失败和降级状态诚实可见。
- 每个轨迹节点跳转到现有真实专业页面或成果，不复制业务状态和写操作。
- Excel / Word 成果能追到 Task、Run、Skill、成果版本、哈希和复核轮次；可信经验候选能追到来源 Task 和成果。
- 候选、已确认、已提升、已撤销和疑似失效状态显示正确；没有形成候选不阻止业务 Task 完成。
- 聚合层异常时，现有 Excel 填价、风险预警、报告、问答和智能协同仍可按原路径运行；页面显示“任务轨迹暂不可用”，不得拖垮专业主流程。

### UI 验收

- 不新增左侧一级菜单，不破坏现有菜单顺序和页面切换。
- 当前任务条紧凑，不显著压缩 Excel、报告和聊天主工作区；1366、1440、1920 宽度及右侧 Dock 展开状态均无横向溢出。
- 字体、字号、按钮、状态色、边框和间距通过项目 UI 规范检查；无 `9px / 10px` 可见业务文字，无卡片套娃、渐变和常驻阴影。
- 在浏览器运行态核对 computed `font-family / font-size / font-weight / line-height`、键盘焦点、减少动态效果和控制台告警。

### 工程与回归验收

- 为 Task 身份映射、幂等创建、旧编号关联、状态规范化、事件排序、重试、退回轮次、成果血缘和无候选场景补后端专项测试。
- 为页面切换不丢 Task、空状态、真实阶段、窄宽度折叠和节点跳转补前端测试。
- 运行 `python tools/check_prd_consistency.py --no-write`、`python tools/check_ui_design_system.py`、前端专项与 `npm run frontend:build`；实现涉及后端时运行 `python -m pytest backend/tests -v`。
- 使用 `08-测试与演示/测试-V3.1-260802/` 现行输入完整跑通“Task 创建 → Skill 冻结 → 匹配 → 风险 / 人工复核 → Excel / Word → 协同 / 经验追溯”，并与现行标准答案核对，证明 Task 层没有改变三个数字和正式成果。
- 自动化测试、浏览器运行态、V3.1 业务结果和 8 分钟演示金线分别记录证据；不得只以 UI 截图或接口返回 200 判定模块完成。

## 本阶段不做

- 不新增左侧“Task 中心”。
- 不把普通知识问答或每一轮聊天自动创建为业务 Task。
- 不一次性重命名或删除现有 `job_id`、`run_id`、协同 `task_id` 和历史数据库字段。
- 不让统一任务层成为第二套专业状态、审核状态或知识治理状态真相。
- 不让大模型生成价格、系数、风险等级、完成状态或审核结论。
- 不自动合并同名项目、同名文件或缺少可靠来源的历史任务。
- 不因包装 `Task / Tool / Experience` 而引入新的平行 UI 设计系统。
