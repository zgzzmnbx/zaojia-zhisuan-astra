# 比赛演示功能回归测试流程

适用范围：大幅改动后、正式发布前，以及比赛现场演示前。每次使用新的测试任务和测试成果；原始样例和标准答案只读。执行人、时间、版本、任务与证据应逐次记录，不能用旧版本通过记录代替本次验收。

## 1. 测试资料与准备

- 输入：`07-测试和演示例子/【演示】-2026年8月22日/【项目例子】【测试输入】可行性研究勘察测量控制价计算 -v3.1【演示】 .xlsx`。SHA-256：`58736e3bce4670fda6d5408acc189d51ed2902e0ffdeb531750cf8daa0a667`。保留文件名中的完整 `【演示】`。
- Excel 标准答案：`07-测试和演示例子/测试-V3.1-260802/【答案-对应版本v3.1】【输出】-控制价计算表-20260802-0123-隐藏空行.xlsx`。SHA-256：`671351f7a542c9ea4bc604621fee95dd0535f0614fe3c7b458b62681c4717b91`。
- Word 参考答案：同目录 `【答案-对应版本v3.1】【输出】-控制价报告-.docx`。SHA-256：`b3e107087080adf8ab058fd5c1b185a99ab9a465ea2800b9ca0f901c19ec9dd5`。
- 确认正式启动入口、版本、运行目录和备份，参见 [正式运行与发布保护](09-正式运行与发布保护.md)。不得清理正式业务数据。核对两个平台应用、网络、受众及接收实例；同一应用只允许一套系统保持长连接，发现冲突时先排查，不擅自切换。
- 标准答案回归口径：启用识别出的工作表与建议字段映射；输出匹配报告，纵向和横向合并均开启，仅匹配“数量”有值的行；下载 Excel 时隐藏数量为空的行。记录本次实际设置；不同设置的结果不能直接判为标准答案回归通过。
- 建议在 `Codex-Temp/` 下按日期和版本建立独立证据目录，保存截图、下载成果、对比结果和测试记录，避免覆盖历史证据与原资料。不要记录凭据或密钥。

## 2. 执行顺序和通过标准

| 步骤 | 操作 | 通过标准与证据 |
| --- | --- | --- |
| 1 上传和转换 | 用正式入口新建独立测试任务，上传上述完整输入；核对文件名、识别出的工作表、表头和映射，按第 1 节口径转换。 | 文件可上传；结构、映射和预览可查看；任务身份明确，转换完成且无错误。记录版本、任务/job ID 和设置。 |
| 2 批量匹配 | 从该任务执行“开始批量匹配”，查看结果、表格和费用汇总。 | 匹配完成，Excel 和基础报告可生成、查看和下载；数据属于同一个任务及成果版本。保留匹配摘要和成果。匹配是真实规则与计价库处理，不因演示文件名变为固定答案。 |
| 3 经验池风险预警 | 在同一任务点击“检查经验池预警”，查看全部风险与依据，点击定位风险行。 | 检查有明确完成状态；风险内容、数值、依据和表格定位一致，不把“未检查”当作零风险。核对表2第5行基价 500000 与经验均值 4274、表3第6行系数 1.3 与经验均值 1.15 等演示重点；如果实际结果不同，记录证据并排查，不能仅凭固定报告正文判通过。 |
| 4 Excel 对照 | 下载“隐藏空行”的当前 Excel 副本，与第 1 节标准答案对照。 | 工作表齐全；三项业务数值（基价/单价、实物系数、技术系数）、公式、匹配状态、目标填色、隐藏行与全表值差异均为 0，或逐项记录并经业务人员确认差异原因；未解释差异不得判通过。核对公式计算状态，待重算不冒充已确认。 |
| 5 报告 | 在风险检查后显式执行“生成报告/补充风险报告”，查看并下载当前 Word；与参考 Word 核对业务内容，在 Word 或 WPS 中打开检查版面。 | 报告打开、预览和下载正常，项目与当前成果对应，风险事项完整且无明显截断、乱码或错页；业务核心与参考答案一致，日期、输入文件名等合理差异单独记录。演示文件会产生固定风险正文，页面应说明预设、未调用模型；该正文的数字固定，不能替代当前风险检查或真实模型验收。 |
| 6 飞书复核 | 选飞书，核对接收人是 **大尾巴**，确认发送当前测试成果和复核卡；接收端打开成果并提交一次复核意见。 | 发件端分别显示成果和卡片成功，接收端实际收到并打开正确版本；提交后系统收到回执，复核进度、意见、任务和轮次一致。记录脱敏证据和时间。 |
| 7 WeAct 复核 | 选 WeAct，核对接收人是 **石萌**，对同一已核实成果发起测试，并在接收端提交一次复核意见。 | 分别确认成果、卡片实际送达且可打开，回执更新到正确任务和轮次。记录脱敏证据和时间。 |

发出前以页面展示的账号和平台再次核对接收人；遇同名或无法确认身份时停止该平台测试。发送失败仅针对确认失败的内容和平台按界面提示重试，先查回执，避免重复发送。禁止向其他人或群组扩大范围。API 返回成功、健康状态为绿或卡片显示“已发送”，都不能代替接收端实际收到与操作回执。

## 3. 程序化检查与覆盖边界

每轮代码交付按项目规定运行 `npm test` 和 `npm run build`，两者检查代码和构建，不代替上述真实演示链路。

现有 `tools/verify_astra_v31.py` 调用独立测试客户端依次执行结构识别、转换、批量匹配、风险检查、演示报告生成及 Excel/Word 比较；其输入是 `03-Src/engine/08-测试与演示/测试-V3.1-260802/` 的冻结副本。本次核对用户指定输入与 `07-测试和演示例子/测试-V3.1-260802/` 的对应文件哈希一致；执行前仍应核验脚本实际输入和答案哈希。脚本写入固定的 `03-Src/engine/Codex-Temp/acceptance/astra-v31/`，可能覆盖该目录下上次的同名证据；运行前先保存既有证据，切勿清理正式运行目录。

在项目根目录 PowerShell 中，保存上述旧证据后执行：

```powershell
& .\.venv\Scripts\python.exe .\tools\verify_astra_v31.py
```

检查该固定目录下的 `V3.1-Task-P0-验收结果.json` 及实际输出，并将本轮结果复制到本次证据目录。若该 Python 环境不可用，记录阻塞原因，不从未验证的环境推断通过。

脚本的 `passed` 条件检查关键数值、公式、目标填色、复核状态和 Word 业务正文；它还输出隐藏行及全表值差异，但这些差异不在现有 `passed` 判定中。必须逐项查看 JSON 明细，隐藏行与全表值也满足第 2 节标准，才能判定 Excel 对照通过。脚本不验证真实浏览器操作、Office/WPS 排版、真实模型、平台实际送达和回执；这些分别记录，不得混为一项。
